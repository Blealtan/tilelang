# TileLang Rust Frontend — Design Document

## Overview

The TileLang Rust frontend (`rust/tilelang-rs`) is a **restricted DSL embedded in
Rust** that compiles to TVM TIR (Tensor Intermediate Representation).  It mirrors
the semantics of the Python `tilelang` frontend but enforces an additional constraint:
no host mutable state.  This makes DSL code structurally similar to pure functional
code, which is both easier to reason about and easier to lower into an IR.

The frontend is split into four crates:

```
tilelang-rs-ffi          generated FFI wrappers (stubgen)
tilelang-rs-core         DSL runtime semantics and IR-builder primitives
tilelang-rs-macros       proc-macro: #[tl_ir] precheck + AST lowering
tilelang-rs              public facade: re-exports, examples, integration tests
```

---

## 1. Overall Architecture

```
User code (#[tl_ir] fn)
        │
        ▼
tilelang-rs-macros
 ├── Precheck (rejects mut, &mut, host assign)
 ├── Tensor-param stripping
 ├── named_let transform
 ├── for  →  ctx.for_each(dsl, |ctx, vars| { ... })
 └── if   →  ctx.if_stmt(cond, then_fn, else_fn)
        │
        ▼
tilelang-rs-core
 ├── BuilderContext         manages IRBuilder + module/func frames
 ├── ForDsl trait           unified entry point for all loop types
 ├── language module        T::kernel, T::parallel, T::serial, T::dynamic, T::ceildiv, dtypes
 ├── Tensor / Buffer        two-phase buffer API
 ├── Expr newtype           arithmetic op overloads
 ├── IntoPrimExpr/Exprs     conversion trait hierarchy
 ├── Nameable / autoref     named_let specialization infrastructure
 └── pred module            predicate helpers (lt, eq, and, or, not, …)
        │
        ▼
tilelang-rs-ffi (TVM C++ runtime)
 └── ffi::script::ir_builder::*   TIR builder calls
```

---

## 2. Three-Crate Split Rationale

| Crate | Concern | Stability |
|---|---|---|
| `tilelang-rs-ffi` | Raw FFI, regenerated by `tvm-ffi-stubgen` | Unstable (auto-generated) |
| `tilelang-rs-core` | Semantic primitives, safe wrappers | Stable internal API |
| `tilelang-rs-macros` | AST rewrite only, calls into `core` | Follows `core` |
| `tilelang-rs` | Public stable API | Stable user-facing |

The key invariant is that **macro lowering is a thin syntactic transform**.  All
semantic logic lives in `tilelang-rs-core`.  This means:

- New loop types are added by implementing `ForDsl` in `core`; the macro needs no change.
- New nameable types are added by implementing `Nameable` in `core`; the macro needs no change.
- New predicate ops are added to `core::pred`; the macro only needs updating if new
  syntax sugar is desired (currently `&&` / `||` / `!` are the only special cases).

## 3. DSL Design Principles

### 3.1 No Host Mutable State

The `#[tl_ir]` macro enforces:

- No `let mut` bindings
- No `mut` parameters or patterns
- No `&mut` references
- No host assignments (`x = …`, `x += …`)

This ensures every binding in the function body is a **single-assignment IR value**,
not a Rust host variable that could diverge from TIR semantics.

The only exception is `alloc_var` + `load`/`store`, which models a TIR local buffer
(an actual memory allocation in the IR, not a host variable).

### 3.2 Two-Phase Buffer API

Buffers go through two phases before being usable:

```
Tensor::new()          zero-cost placeholder (ZST in Rust)
    │ .declare(shape, dtype)
    ▼
PendingBuffer          holds ffi::tir::Buffer, Arg not yet registered
    │ named_let → apply_name("x")
    ▼
Buffer                 Arg("x", buffer) registered in IR; load_at / store_at usable
```

The split exists because the IR requires a name for each buffer argument (for
`T.match_buffer`), but the user writes `let a = a.declare(...)` where "a" is the
natural name.  The `named_let` transform automatically injects "a" as the IR name.

Using `Tensor::new().declare_named(shape, dtype, "A")` bypasses named_let and
registers the name immediately (Phase-2 compatibility, useful without `#[tl_ir]`).

### 3.3 `ForDsl` Trait — Unified Loop Entry

All loop types implement the same trait:

```rust
pub trait ForDsl {
    fn enter(self) -> (IRBuilderFrame, Array<Var>);
}
```

`BuilderContext::for_each` is the sole loop primitive:

```rust
pub fn for_each<D, T, F>(&self, dsl: D, f: F) -> T
where
    D: ForDsl,
    F: FnOnce(&Self, Array<ffi::tir::Var>) -> T,
```

The macro lowers every `for pat in expr { body }` to:

```rust
ctx.for_each(expr, |ctx, __vars| {
    let pat = FromLoopVars::bind1(__vars);  // or bind2/bind3/bind4 for tuples
    body
});
```

Because `F: FnOnce`, the closure body runs exactly once (the IR builder records the
loop structure, not Rust iterations).  This means an `Expr` value can be moved into
the inner closure without `.clone()`.

## 4. `Expr` Newtype and Operator Overloads

`ffi::tir::Var` and `ffi::ir::PrimExpr` are foreign types — Rust's orphan rule
prevents implementing `std::ops::Add` etc. on them directly.

The `Expr` newtype wraps `PrimExpr` and implements all four arithmetic operators
parametrically:

```rust
impl<R: IntoPrimExpr> std::ops::Add<R> for Expr { ... }
impl<R: IntoPrimExpr> std::ops::Sub<R> for Expr { ... }
impl<R: IntoPrimExpr> std::ops::Mul<R> for Expr { ... }
impl<R: IntoPrimExpr> std::ops::Div<R> for Expr { ... }
```

The right-hand side accepts anything that implements `IntoPrimExpr`, including
`i64`, `Var`, `&Var`, `PrimExpr`, `&PrimExpr`, and `Expr` itself.

To use arithmetic on a loop variable `bx: ffi::tir::Var`, wrap it once:

```rust
let start_x = Expr::from(&bx) * block_n;
```

## 5. `IntoPrimExpr` / `IntoPrimExprs` Conversion Traits

### `IntoPrimExpr` (single value)

Implemented for: `PrimExpr`, `&PrimExpr`, `Var`, `&Var`, `Expr`, `&Expr`,
`i32`, `i64`, `u32`, `u64`, `isize`, `usize`, `IntImm`.

All implementations are infallible and clone-on-reference where needed.

### `IntoPrimExprs` (collection of values → `Array<PrimExpr>`)

```
IntoPrimExprs
├── impl<T: IntoPrimExpr> for T          → 1-element array (scalar)
├── impl<T: IntoPrimExpr, const N> for [T; N] → N-element array
├── impl<A: IPE, B: IPE> for (A, B)     → 2-element array
├── impl<A, B, C> for (A, B, C)         → 3-element array
└── impl<A, B, C, D> for (A, B, C, D)  → 4-element array
```

The scalar impl and the array impl do not conflict because `[T; N]` does not
implement `IntoPrimExpr`.

This trait is used uniformly for buffer indices (`load_at`, `store_at`), parallel
extents, and kernel grids, keeping the call sites consistent.

## 6. `named_let` — Autoref Specialization

The `named_let` transform injects a variable's Rust binding name into the IR.
It is based on the [dtolnay autoref specialization technique][autoref].

[autoref]: https://github.com/dtolnay/case-studies/tree/master/autoref-specialization

### Mechanism

For every `let x = expr;` where `x` is a plain identifier with an init expression,
the macro generates:

```rust
let x = {
    #[allow(unused_imports)]
    use ::tilelang_rs_core::PassthroughTag as _;
    let __val = expr;
    (&__val).__tl_named_tag().apply(__val, "x")
};
```

Method resolution works as follows:

1. If `__val` has an **inherent** `__tl_named_tag(&self) -> NameableKind` method,
   that method is called (inherent methods take priority over trait methods).
   `NameableKind::apply` delegates to `Nameable::apply_name`, which registers the
   buffer argument name in the IR and returns a `Buffer`.

2. Otherwise, the blanket `PassthroughTag` trait impl is used (brought into scope
   by the `use` statement), returning `PassthroughKind`.
   `PassthroughKind::apply` is a no-op that returns `__val` unchanged.

### Extending to new nameable types

To make a new type `Foo` participate in `named_let`:

1. Add an inherent method: `pub fn __tl_named_tag(&self) -> NameableKind { NameableKind }`.
2. Implement `Nameable for Foo` with the desired `Named` associated type and
   `apply_name` logic.

No changes to the macro or to `NameableKind`/`PassthroughKind` are required.

## 7. `#[tl_ir]` Macro Expansion Flow

Given:

```rust
#[tl_ir]
fn vector_add(a: T::Tensor, b: T::Tensor, c: T::Tensor) {
    let n = T::dynamic("n", T::INT64);
    let a = a.declare(&n, T::FLOAT32);
    for bx in T::kernel(T::ceildiv(&n, 2048i64)).threads(128i64) {
        let start_x = Expr::from(&bx) * 2048i64;
        for ix in T::parallel(2048i64) {
            let x = start_x + &ix;
            c.store_at(&x, a.load_at(&x) + b.load_at(&x));
        }
    }
}
```

The macro produces:

```rust
fn vector_add() -> ::tilelang_rs_core::Result<::tilelang_rs_core::ffi::ir::IRModule> {
    // (1) Runtime init — only ? in the whole function
    let __ctx = ::tilelang_rs_core::BuilderContext::new("vector_add")?;

    // (2) prim_func frame
    __ctx.with_tir_prim_func("vector_add", false, |_prim_func| {

        // (3) Tensor param injection (params stripped from signature)
        let a = ::tilelang_rs_core::Tensor::new();
        let b = ::tilelang_rs_core::Tensor::new();
        let c = ::tilelang_rs_core::Tensor::new();

        // (4) named_let for `n` (passthrough — Var is not Nameable)
        let n = { let __val = T::dynamic("n", T::INT64); (&__val).__tl_named_tag().apply(__val, "n") };

        // (5) named_let for `a` (Nameable — PendingBuffer → Buffer via Arg registration)
        let a = { let __val = a.declare(&n, T::FLOAT32); (&__val).__tl_named_tag().apply(__val, "a") };

        // (6) for → for_each
        __ctx.for_each(T::kernel(T::ceildiv(&n, 2048i64)).threads(128i64), |__ctx, __vars| {
            let bx = ::tilelang_rs_core::FromLoopVars::bind1(__vars);

            // (7) named_let for `start_x` (passthrough — Expr is not Nameable)
            let start_x = { let __val = Expr::from(&bx) * 2048i64; (&__val).__tl_named_tag().apply(__val, "start_x") };

            // (8) inner for → for_each
            __ctx.for_each(T::parallel(2048i64), |__ctx, __vars| {
                let ix = ::tilelang_rs_core::FromLoopVars::bind1(__vars);

                // (9) named_let for `x` (passthrough); start_x moved by +
                let x = { let __val = start_x + &ix; (&__val).__tl_named_tag().apply(__val, "x") };

                c.store_at(&x, a.load_at(&x) + b.load_at(&x));
            });
        });
    });

    // (10) finalize
    Ok(__ctx.finish_ir_module())
}
```

### Key invariants

- Step (1) is the only place `?` appears — all other operations panic internally
  on unexpected FFI failure (`expect`).
- Steps (4)–(9) all go through `named_let`; the transform fires for every
  `let ident = expr;` binding.
- Step (3) injects `Tensor::new()` for each stripped `T::Tensor` parameter.
  The user's `let a = a.declare(...)` at step (5) then provides the shape/dtype
  and the named_let transform provides the name.

## 8. Dtype Constants

All common data types are available as `pub const` values in the `language` module,
using `DLDataTypeCode` enum variants (no magic numbers):

```rust
pub const FLOAT32:  DLDataType = dl(DLDataTypeCode::kDLFloat,  32);
pub const INT64:    DLDataType = dl(DLDataTypeCode::kDLInt,    64);
pub const BFLOAT16: DLDataType = dl(DLDataTypeCode::kDLBfloat, 16);
// ... INT4/8/16/32, UINT8/16/32/64, FLOAT16/64, all float8/float6/float4 variants
```

The `DLDataTypeExt` trait adds `.with_lanes(n)` for vector dtypes:

```rust
T::INT8.with_lanes(4)  // → int8x4
```

## 9. Comparison with the Python Frontend

| Python | Rust (`#[tl_ir]`) |
|---|---|
| `T.dynamic("n", "int64")` | `T::dynamic("n", T::INT64)` |
| `T.match_buffer(a, [n])` | `let a = a.declare(&n, T::FLOAT32);` |
| `T.Kernel(grid, threads=128)` | `T::kernel(grid).threads(128i64)` |
| `T.Parallel(extent)` | `T::parallel(extent)` |
| `T.serial(start, stop)` | `T::serial(start, stop)` |
| `A[i]` (read) | `a.load_at(&i)` |
| `C[i] = v` (write) | `c.store_at(&i, v)` |
| `A[i] + B[i]` | `a.load_at(&i) + b.load_at(&i)` |
| `T.ceildiv(a, b)` | `T::ceildiv(&a, b)` |
| `T.int64(x)` | `x as i64` (literal) |

The primary structural difference is that Rust requires explicit type annotations
at buffer declaration time (`T::FLOAT32`) and uses method syntax for load/store,
while Python uses subscript syntax and infers dtypes from numpy arrays.

## 10. Extending the DSL

### Adding a new loop type

1. Define a new `FooDsl` struct in `tilelang-rs-core/src/lib.rs`.
2. Implement `ForDsl for FooDsl`: call the appropriate `ffi::...` constructor,
   extract vars, return `(frame.into(), vars)`.
3. Add a `T::foo(...)` constructor in the `language` module.
4. Add a smoke test in `tilelang-rs-core/tests/`.

No macro changes required.

### Adding a new nameable type

1. Add an inherent method `pub fn __tl_named_tag(&self) -> NameableKind`.
2. Implement `Nameable` with appropriate `Named` type and `apply_name` logic.
3. Add a test in `tilelang-rs-macros/tests/runtime_ir.rs`.

No macro changes required.

### Adding buffer intrinsics (`T.copy`, `T.alloc_shared`)

1. Add the FFI call wrapper in `tilelang-rs-core`.
2. For `alloc_shared`/`alloc_fragment`: these allocate into a frame, so they
   follow the same `named_let` pattern as `Tensor::declare` if they return a
   nameable type.
3. For `T.copy`: this is a `tir.Call` intrinsic; wrap it as a `Buffer` method
   or a free function in the `language` module.
4. Update the public re-exports in `tilelang-rs/src/lib.rs`.
